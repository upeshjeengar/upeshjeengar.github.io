The core idea

Data engineering is the nervous system of an ML product.

Modern applications collect data easily: phones, web apps, sensors, payments, logs, clicks, messages, and background jobs create a constant stream of signals. The hard part is not collecting data. The hard part is making data reliable enough that models, products, and people can use it without guessing what it means.

Rule of thumb: storage format, schema, and dataflow choices are product decisions. A model trained on stale, inconsistent, or poorly transported data inherits those problems, no matter how clever the algorithm is.

Storage formats

Choose the file format based on access pattern.

A format is a promise about how data will be written and read. Human-readable formats are convenient while debugging. Machine-optimized formats are better when volume, speed, and cost matter.

Format Best use Design tradeoff
JSON APIs, logs, semi-structured payloads, human inspection. Flexible and readable, but verbose. It can waste space and slow down analytics scans.
CSV Simple tabular exports and row-by-row ingestion. Easy to write and share, but weak on types, nested data, and schema guarantees.
Parquet Analytics, feature tables, large datasets, column-level queries. Harder for humans to inspect, but compact and fast when queries touch only some columns.

Row-major thinking

CSV stores records row by row. That works well when the system usually needs the whole record: user id, timestamp, item, price, and status together.

Column-major thinking

Parquet stores values column by column. That shines when a query needs only a few features from a wide dataset with hundreds or thousands of columns.

i
Text versus binary

Text formats are easier to read. Binary formats are built for machines. In production analytics, binary columnar formats usually reduce storage, network transfer, and query time.

Data models

Data model depends on who needs the data.

Data model is not the data itself. It is the shape of the data for a particular user, system, or purpose. The same object can be modeled differently depending on what the system needs to decide.

A

Consumer view

A car listing highlights mileage, price, color, features, images, and financing options.

B

Operations view

A fleet system cares about vehicle id, service history, availability, location, and maintenance risk.

C

Authority view

A registration system cares about owner records, license plates, permits, and compliance status.

Relational databases

Relational systems organize data in tables. Rows have no inherent order, and relationships between entities are expressed through keys. They are strong when the schema is stable, consistency matters, and teams need reliable queries.

Normalization organizes tables to reduce duplication and avoid anomalies: accidental corruption, inconsistent updates, or data loss caused by storing the same fact in too many places.

Non-relational databases

NoSQL systems often trade strict relational structure for flexible schema management, scale, or access patterns like documents, key-value lookups, graphs, or wide-column storage.

That flexibility is useful, but it moves responsibility into application code, data contracts, and operational discipline.

Warehouse vs lake

Store clean answers and raw possibilities differently.

Data warehouse

  • Structured data prepared for analytics.
  • Optimized for reporting, dashboards, SQL, and business questions.
  • Best when users need trusted, repeatable answers.

Data lake

  • Raw or semi-processed data in many formats.
  • Useful before preprocessing, feature engineering, or exploration.
  • Best when teams need flexibility and future reuse.
Need dashboards? Warehouse. Need raw logs? Lake. Need ML features? Often both. Need governance? Design it early.

Transactions

ACID is the reliability contract for database changes.

A transaction is a unit of work over data: create, read, update, or delete. OLTP systems handle many of these operations every day. ACID properties explain what must stay true when transactions run, fail, or collide.

A

Atomicity

All or nothing. If one step fails, the whole transaction rolls back.

C

Consistency

The database moves from one valid state to another valid state.

I

Isolation

Concurrent transactions should not corrupt or unexpectedly see each other's partial work.

D

Durability

Once committed, data survives crashes, restarts, and power loss.

In an ML system, ACID thinking matters anywhere labels, features, payments, user actions, or model decisions must be auditable. If a training record can silently disagree with product truth, debugging becomes guesswork.

Modes of dataflow

Microservices need a way to exchange facts.

When systems split into services, data has to move between them. The simplest design is direct communication. The scalable design often introduces a broker or event bus so services do not need to know about every other service.

1

REST API

A service exposes HTTP endpoints such as GET, POST, PUT, or DELETE. JSON is common because it is easy to send and debug.

2

RPC

A remote procedure call feels like invoking a local function, but the work happens on another service with serialized parameters and responses.

3

Shared database

One process writes and another reads. This can be simple, but it also couples services through schema, timing, and ownership.

4

Broker or event bus

Services publish messages to a broker. Interested consumers subscribe, process, store, or forward the data without forcing one-to-one service wiring.

!
The direct-call problem

One-to-one service connections increase latency, operational overhead, and debugging pain. When a dependency crashes, callers often learn only after timeout. Event-driven design gives systems a cleaner way to decouple producers from consumers.

Pub/sub

Publish once, let every subscriber react.

In publish/subscribe architecture, a producer(microservice 1) publishes events to a topic. Consumers(microservice 2, microservice 3, etc.) subscribe to the topics they care about. The publisher does not need to know who receives the event.

That pattern is why tools such as Apache Kafka, Amazon SNS, and Amazon Kinesis are common in data platforms. A single clickstream, payment event, or model prediction can feed analytics, monitoring, notifications, feature stores, and downstream products.

Think of a topic like a channel. The publisher uploads once. Subscribers receive what they need without the publisher maintaining a private connection to each one.

What is a Topic?

A named stream of events, such as orders-created, page-views, or model-predictions.

Retention

Messages are often kept for a fixed time before archival or deletion. Permanent storage might live in S3 or a data lake.

Queue alternative

Message queues such as RabbitMQ or Amazon MQ are often better for one-to-one task processing and worker distribution.

Processing modes

Batch and stream processing optimize different clocks.

Batch processing

  • Works over large chunks of historical data.
  • Good for daily metrics, offline training, backfills, and audits.
  • MapReduce is the classic example: read the dataset, process it, then return results.

Stream processing

  • Processes events continuously as they arrive.
  • Good for alerts, fraud checks, recommendations, real-time features, and live dashboards.
  • Designed for low latency, but it requires more care around ordering, retries, and late data.

Where Spark fits

Apache Spark is useful because it can handle both batch and streaming-style workloads. Its in-memory execution model makes many jobs faster than older disk-heavy processing patterns.

Where ML fits

Training often starts as a batch job. Serving and monitoring often behave like streams. Mature ML systems usually need both clocks: historical learning and live reaction.

Design playbook

Questions to ask before choosing a data architecture.

Before storage

Who reads this data? Do they read whole records or a few columns? Is schema flexibility more important than consistency?

Before dataflow

Does the consumer need an immediate response, or can it react to an event? How many consumers need the same data?

Before processing

Is freshness measured in seconds, minutes, hours, or days? What happens when data arrives late or out of order?

OK
The practical answer

Start with the simplest architecture that protects correctness. Add brokers, streams, binary formats, and distributed processing when volume, latency, reliability, or team boundaries make them necessary.
