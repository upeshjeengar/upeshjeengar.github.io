Part 5 - Model Development

A strong model begins with the right problem.

Model development is more than selecting an algorithm. It is an iterative process of framing the task, choosing objectives, running reproducible experiments, debugging failures, and deciding whether offline evidence is strong enough for production.

The core idea

The algorithm is only one decision in model development.

After preparing training data and engineering features, we can begin developing the model. This stage is iterative: every run gives us evidence about the problem, the data, the implementation, and the production constraints.

A model can achieve a strong benchmark score and still be unsuitable for production. It may be too slow, expensive, unstable, difficult to explain, poorly calibrated, or weak on an important subgroup. The real goal is therefore not to find the most impressive algorithm. It is to find a model and operating setup that solve the intended problem reliably.

A useful model is not simply the one with the highest offline score. It is the one whose behavior, cost, and failure modes fit the system around it.

Problem framing

A business problem is not automatically an ML problem.

Suppose a bank wants to make customer support faster. That request does not yet define what a model should learn. If the bottleneck is routing incoming requests, we can frame the task as predicting the correct department from the request text.

1

Input

Define what information will be available when a prediction is made, such as the text of a support request.

2

Output

Define what the system must produce, such as one of four destination departments.

3

Objective

Define what learning should optimize, such as reducing the difference between predicted and correct routes.

Common task types

TaskOutputExampleMain challenge
RegressionA continuous valuePredicting the price of a houseSelecting a loss and handling the scale of errors
Binary classificationOne of two classesFraudulent or legitimate transactionChoosing a threshold and balancing false positives against false negatives
Multiclass classificationExactly one of several classesRouting a request to one departmentClass imbalance and confusing similar classes

Cardinality changes the difficulty

A multiclass problem with five classes is different from one with fifty thousand. High-cardinality classification requires enough examples for every class, including rare ones. A hierarchical design can reduce the difficulty: first predict a broad category, then predict a subgroup inside that category.

The same product goal can have multiple ML formulations

Consider predicting which app a person will open next. One formulation treats every installed app as a class and produces a probability distribution over all apps. This becomes difficult to maintain because adding a new app can change the model output space and require retraining.

A more flexible formulation scores each candidate app independently. The model receives user, environment, and app features, then returns a value representing how likely the person is to open that app. A new app becomes a new input candidate instead of a new output class.

Classify across all apps

  • One prediction produces scores for every app.
  • The output dimension depends on the app catalog.
  • Adding classes can force architecture changes or retraining.

Score each app

  • Each user-app pair receives one score.
  • The same model can evaluate new candidates.
  • Serving requires scoring and ranking multiple apps.

Objective functions

The loss teaches the model what counts as a mistake.

Supervised learning compares predictions with ground-truth labels. Regression commonly uses losses such as mean absolute error or root mean squared error, binary classification often uses log loss, and multiclass classification commonly uses cross-entropy.

cross_entropy(y, p) = -sum(y[i] * log(p[i]))

# If the correct class is politics:
y = [0, 0, 0, 1]
p = [0.45, 0.20, 0.02, 0.33]

# Only the probability assigned to the correct class contributes:
loss = -log(0.33)

The objective function is a design decision, not a neutral implementation detail. When a product has several goals, forcing all of them into one weighted loss can make both training and maintenance harder.

Decouple objectives when their behavior differs

A newsfeed may need to remove spam, remove unsafe content, estimate quality, and predict engagement. Quality and engagement can conflict. One model could optimize a combined loss, but every change to the weights may require retraining.

combined_loss = alpha * quality_loss + beta * engagement_loss

An alternative is to train separate quality and engagement models, then combine their outputs during ranking.

ranking_score = alpha * quality_score + beta * engagement_score

This separation allows the team to adjust ranking weights without retraining both models. It also lets components evolve on different schedules. A spam detector may need frequent updates because attackers adapt quickly, while the definition of content quality may change more slowly.

Model selection

Select for the real system, not only the validation set.

Classical ML and neural networks are not mutually exclusive generations of technology. Tree-based models remain strong for structured data and strict latency limits, matrix factorization still supports recommendation systems, and simpler models often work alongside neural networks.

Compare candidates using the properties that matter for your application: predictive quality, label requirements, training cost, inference latency, memory use, interpretability, ease of deployment, and expected maintenance.

1

Avoid the SOTA trap

A model that leads a static academic benchmark may be too slow, expensive, or fragile for your data and serving environment.

2

Start simple

A simple model validates the pipeline, gives you a baseline, and makes problems easier to isolate before complexity grows.

3

Compare fairly

Human enthusiasm affects how much tuning each architecture receives. Use comparable data, budgets, search effort, and metrics.

4

Consider future gains

The best model today may not remain best as data grows. Learning curves help show whether more examples are likely to help.

5

Evaluate trade-offs

Accuracy competes with latency, compute, interpretability, and different error costs. The product decides which trade-off is acceptable.

6

Know assumptions

A model is useful only when assumptions about the data and target are close enough to reality.

Assumptions worth checking

AssumptionQuestion to ask
PredictabilityDoes the input contain enough information to predict the target at inference time?
IID dataAre examples drawn independently from a sufficiently stable distribution?
SmoothnessShould similar inputs normally produce similar outputs?
Decision boundaryCan the chosen model family represent the relationship in the data?
Conditional independenceFor a model such as Naive Bayes, is the simplifying relationship between features reasonable enough?
Distribution shapeDoes a statistical method depend on normality or another distribution that the data does not follow?

Ensembles

Different errors are more valuable than more models.

An ensemble combines several base learners. For classification, the final decision can use majority voting; for regression, it can average predictions. The gain comes from diversity: when all base learners make the same errors, combining them adds little.

For intuition, suppose three independent classifiers are each correct 70% of the time. A majority vote is correct when all three are correct or exactly two are correct:

P(ensemble correct)
  = 0.7^3 + 3 * (0.7^2 * 0.3)
  = 0.343 + 0.441
  = 0.784

The ensemble reaches 78.4% under the independence assumption. Perfectly correlated models would remain at 70%, which is why mixing different model families, features, or training samples can matter.

Bagging

Train learners on bootstrap samples created by sampling with replacement. Voting or averaging reduces variance and can stabilize models that overreact to the training set. Random forests add feature randomness to this idea.

Boosting

Train weak learners sequentially, increasing attention on examples the current ensemble handles poorly. Gradient boosting, XGBoost, and LightGBM follow this family of ideas.

Stacking

Train base learners, then train a meta-learner on their outputs. The combiner can be a simple average or another model such as logistic regression.

!
Production cost still matters.

Ensembles can improve predictive performance, but they increase serving latency, deployment complexity, monitoring needs, and maintenance. They are most attractive when a small quality gain has substantial value.

Experiment tracking

A promising run is useful only if you can explain and reproduce it.

Small changes in learning rate, data, code, or random initialization can produce very different results. Experiment tracking records what happened during a run; versioning records enough of the inputs and environment to recreate it later.

Track the signals that help you decide or debug

Model behavior

Training and validation loss, task metrics such as F1 or perplexity, prediction examples, and artifacts such as curves or evaluation reports.

Training behavior

Learning rate, gradient norms, weight norms, throughput, steps or tokens per second, and checkpoint progress.

System behavior

CPU and GPU utilization, memory consumption, input pipeline speed, and evidence of resource bottlenecks.

Reproducibility context

Code revision, data version, configuration, dependency versions, hardware, random seed, and the command used to start the run.

Logging everything can become noisy. Track broadly enough to investigate failures, but make the few decision-critical metrics easy to find.

Data versioning is harder than code versioning

Datasets can be too large to duplicate, binary records do not produce useful line-by-line diffs, and data may not fit on every developer’s machine. Privacy rules can also require deletion of user records, making perfect historical reconstruction legally impossible. Reproducibility therefore depends on data identifiers, lineage, transformations, environment metadata, and retention policy, not only a Git commit.

Debugging

ML systems can fail silently.

Traditional software often fails with an exception or crash. An ML pipeline can complete normally, show decreasing loss, and still produce incorrect predictions. Validation is also slow because checking a fix may require retraining.

Failures may come from incompatible model assumptions, implementation mistakes, poor hyperparameters, incorrect labels, outdated normalization statistics, weak features, leakage, or infrastructure. These components are often owned by different teams, which makes diagnosis a system problem rather than only a modeling problem.

1

Start with the smallest working model

Add components gradually and measure what each one changes. Complexity introduced all at once creates too many possible failure points.

2

Overfit one small batch

Train and evaluate on a tiny sample. If the model cannot nearly memorize ten images or a small set of sentence pairs, investigate the implementation before tuning generalization.

3

Control randomness

Fix random seeds for initialization, shuffling, and stochastic layers while debugging. This helps separate code changes from random variation.

Distributed training

Scaling compute introduces new optimization problems.

Large datasets may not fit in memory, and large models may not fit on one accelerator. The system then needs parallel preprocessing, shuffling, batching, communication, and checkpointing as well as a learning algorithm.

Gradient checkpointing trades additional computation for lower memory use by discarding selected activations during the forward pass and recomputing them during backpropagation. This can fit larger models or larger batches on the same hardware.

Data parallelism

  • Each worker holds a copy of the model.
  • Workers train on different data batches.
  • Gradients must be combined across workers.
  • Synchronous updates suffer from stragglers.
  • Asynchronous updates risk stale gradients.

Model parallelism

  • Different model components live on different workers.
  • Dependencies between layers can leave workers idle.
  • Pipeline parallelism splits batches into micro-batches.
  • Communication and scheduling become part of model performance.
  • It can be combined with data parallelism.

A larger number of workers also creates a larger effective batch size. Increasing the learning rate can compensate up to a point, but very large batches eventually provide diminishing returns and can destabilize optimization. Hardware utilization, network communication, and workload balance must be measured together.

AutoML

Automation ranges from tuning parameters to designing models.

The most common production form of AutoML is hyperparameter tuning. Learning rate, batch size, depth, hidden dimensions, dropout, optimizer settings, and numerical precision can all change performance substantially.

ApproachWhat it searchesTrade-off
Grid searchA predefined combination of parameter valuesSimple, but expensive as dimensions grow
Random searchRandom configurations from specified distributionsOften explores large spaces more efficiently than a grid
Bayesian optimizationConfigurations selected using results from previous trialsSample-efficient, but adds optimization complexity
Architecture searchOperations, connections, layers, and model structurePowerful, but computationally expensive
Learned optimizerThe rule used to update another modelPromising research with a high upfront training cost
!
Keep the test set out of the search loop.

Select hyperparameters using validation performance. Use the test split only for the final, less-biased estimate. Repeatedly choosing configurations based on test results turns the test set into another training signal.

Development phases

Earn complexity one phase at a time.

1

Before ML

Try rules, ordering, retrieval, or another simple heuristic. A non-ML solution may already solve enough of the problem.

2

Simplest ML model

Use an interpretable, easy-to-deploy model to validate the framing, labels, features, training pipeline, and serving path.

3

Optimize simple models

Improve objectives, features, data, hyperparameters, and ensembles after the end-to-end framework is trusted.

4

Complex systems

Move to heavier architectures only after simpler approaches reach their limit and the use case justifies a meaningful gain.

Each phase produces the baseline for the next. This makes the value of added complexity measurable instead of assumed.

Offline evaluation

A metric has meaning only in comparison.

Offline evaluation estimates whether a model is ready for production while ground truth is still available. It cannot reproduce every production condition, but it should eliminate models that are inaccurate, fragile, unfair, or operationally unsuitable.

Establish useful baselines

Random

Compare against uniform random predictions and predictions sampled from the observed label distribution.

Simple heuristic

Measure a rule that uses domain knowledge but no learned model, such as ranking feed items by recency.

Zero rule

Always predict the most common class. This exposes misleading scores on imbalanced datasets.

Human

Compare with the people whose work the system will automate or support, especially for high-stakes tasks.

Existing solution

Measure the current rules, vendor, workflow, or production model. A slightly less accurate model may still win on cost or usability.

Previous phase

Use the strongest simpler solution as the baseline for the next development phase.

A strong F1 score can still be meaningless if a random or majority-class predictor achieves the same result. Always report what the model beats, by how much, and at what additional cost.

Behavioral tests

Test how predictions change, not only whether they are correct.

Production inputs are often noisier than development data. Behavioral evaluation makes controlled changes to examples and checks whether the model reacts in a sensible way.

Perturbation tests

Add realistic noise, crop an audio clip, alter compression, introduce a typo, or vary image quality. Prefer models that remain reliable under the disturbances expected in production.

Invariance tests

Change information that should not affect the outcome. A resume score should not change because a name is replaced, and a lending result should not depend on a protected attribute.

Directional tests

Change a feature whose effect should be predictable. With everything else fixed, increasing a house lot size should not reduce the predicted price without a defensible reason.

Calibration and confidence

A probability should describe how often the event happens.

If a model assigns 70% probability to many events, a calibrated model should be correct on about 70% of those events. A model can rank candidates correctly while still producing misleading probabilities.

Calibration matters when probabilities drive decisions: estimating ad clicks, allocating risk, deciding whether a human should review a case, or making recommendations that reflect a user’s actual preferences. Reliability curves compare predicted probabilities with observed frequencies. Methods such as Platt scaling can recalibrate a classifier using held-out data.

# Conceptual calibration check
for probability_bucket in buckets:
    predicted = mean(model_probability)
    observed = mean(actual_outcome)
    compare(predicted, observed)

Confidence is an instance-level decision

Overall accuracy summarizes a population. Confidence asks whether one prediction is reliable enough to use. For low-confidence cases, the system needs an explicit policy: abstain, request more information, fall back to a rule, or route the case to a human.

Return prediction Ask for more input Use a fallback Request human review Abstain safely

Slice-based evaluation

Overall performance can hide the failures that matter most.

A slice is a meaningful subgroup of the evaluation data, such as mobile users, a geographic region, a device type, paid customers, a demographic group, or an uncommon class.

Imagine that 90% of examples belong to a majority group. Model A reaches 98% accuracy on that group but only 80% on the minority group, for 96.2% overall. Model B reaches 95% on both groups, for 95% overall. Selecting only by overall accuracy favors Model A and hides a large subgroup failure.

ModelMajority sliceMinority sliceOverall
Model A98%80%96.2%
Model B95%95%95%

Slices can also have different business importance. In churn prediction, performance on paying customers may matter more than performance on free accounts. Aggregation can even reverse subgroup trends, a phenomenon known as Simpson’s paradox. Therefore, inspect both overall and slice-level evidence before choosing a model.

How to discover critical slices

Domain heuristics

Use product and subject-matter knowledge to define likely differences such as browser, location, device, language, or customer tier.

Error analysis

Review misclassified examples manually and look for repeated characteristics that aggregate metrics conceal.

Automated discovery

Generate candidate slices using clustering, search, or decision-based methods, then rank the groups with unusually poor or unusual behavior.

i
Not every slice failure is a model failure.

Poor mobile performance may reveal a hidden interface, data collection, or instrumentation problem. Fine-grained evaluation can expose issues elsewhere in the product.

Summary

Model development is a chain of evidence.

Begin by framing a broad product need as an ML task with clear inputs, outputs, and objectives. Compare model families under fair conditions, start with the simplest credible baseline, and evaluate operational properties alongside predictive performance.

As the project matures, experiment tracking and versioning make results understandable and reproducible. Debugging practices reduce uncertainty, while ensembles, distributed training, and AutoML provide additional power when the value justifies the complexity.

Finally, offline evaluation should go beyond one aggregate metric. Baselines, perturbation tests, invariance checks, directional expectations, calibration, confidence policies, and slice-based analysis help determine whether a model behaves sensibly before it reaches users. Offline evidence cannot guarantee production success, but it can prevent many avoidable failures.
