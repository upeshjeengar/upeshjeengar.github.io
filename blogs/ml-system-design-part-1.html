The core idea

Machine learning is useful when rules become brittle.

A practical way to think about ML: it learns complex patterns from existing data and uses those patterns to make predictions on data it has not seen before. Each phrase in that sentence is a requirement, not decoration.

Rule of thumb: if a lookup table, SQL query, regex, or a simple heuristic solves the problem reliably and cheaply, start there. ML earns its place when explicit rules become too costly, too fragile, or too slow to update.

System view

The model is just one layer.

When people say “ML system,” they often picture a model. In production, the system includes the user interface, the data stack, training and serving code, deployment infrastructure, monitoring, and the hardware that makes latency and throughput possible.

InterfaceHow users, developers, and downstream services interact with predictions.
DataCollection, storage, labels, validation, feature pipelines, privacy, and data quality.
ML algorithmsModel families, training objectives, features, evaluation, and optimization.
InfrastructureExperiment tracking, CI/CD, model registry, deployment, monitoring, and incident response.
HardwareCPUs, GPUs, memory, network, edge devices, autoscaling, and cost constraints.

Mind vs data

Data is not everything, but without it there is no ML system.

The chapter frames a long-running debate: clever structure versus massive data and computation. In practical production work, the takeaway is not “ignore algorithms.” It is “do not treat data as an afterthought.”

A production data hierarchy

Move / Store
Clean / Transform

Learn / Optimize

More data can still hurt

Outdated records, wrong labels, leakage, biased sampling, duplicate users, and poisoned examples can degrade a model. Production data work is as much about filtering and governance as it is about volume.

🧪
Ask during design reviews:

What data would make this model worse? What data would be uniquely valuable? How will we know when the data distribution has changed?

Research vs production

Leaderboards optimize for a slice of reality.

Research often starts from a clean benchmark and a single objective. Production starts from stakeholders with conflicting constraints and data that shifts under your feet.

      Computation

      Throughput gets you scale. Latency keeps users.

      Training workflows usually reward high throughput. User-facing inference cares deeply about latency: the time from request to response. Batching can improve throughput, but waiting for a batch can increase latency.

      Simplified model: throughput = batch size ÷ processing time. User latency = queue wait + processing time.

      Software 2.0

      ML systems are code + data + learned artifacts.

      Traditional software already teaches useful practices: modularity, testing, CI/CD, observability. ML adds new things to test and version: datasets, labels, features, trained weights, model behavior, and data distributions.

      {} Code

      Training, serving, validation, data transforms, orchestration.

      🗃️Data

      Samples, labels, features, lineage, privacy, quality checks.

      🧠Artifacts

      Weights, feature stores, embeddings, configs, model cards.

      Silent failures are common
      A service can return a prediction without crashing while the prediction is wrong, biased, stale, or no longer useful. That is why observability must include model behavior, not just HTTP 200s.
      Data versioning is hard
      Changing data can change the model even when the code is identical. Reproducibility requires knowing exactly which data, labels, transformations, and parameters created an artifact.
      Model size becomes an engineering constraint
      A large model may improve offline metrics but be too slow, expensive, or memory-hungry for the target device or service-level objective.

      Design goals

      Four production requirements to design for early

      The chapter highlights four characteristics that most ML systems need: reliability, scalability, maintainability, and adaptability. Use the sliders to see how design priorities change.

      Reliability
      The system should keep doing the right thing at the expected performance level even under faults, bad inputs, dependency failures, and human mistakes.
      Scalability
      The system should handle growth in traffic, model count, model size, data volume, and operational complexity without heroic manual work.
      Maintainability
      Different contributors should be able to understand, update, test, and debug their parts of the system without breaking the rest.
      Adaptability
      The system should detect drift, accept improvements, and update models or data pipelines without unacceptable service disruption.

      Stakeholder tension simulator

      Balance is key: start with a simple model, add monitoring, and only pay for complexity when it clears a business or risk threshold.

      Lifecycle

      Production ML is a loop, not a line.

      The naive story is collect data → train model → deploy. The real story has backtracking: wrong labels, class imbalance, stale test data, changing business metrics, and monitoring signals that send you back to scoping.

      Takeaway playbook

      How to use this chapter in your next design review

      Before model development

      Define the business objective, prediction target, input data, labels, failure cost, latency budget, privacy constraints, fairness risks, and launch criteria.

      During model development

      Track data versions, baselines, metrics, feature definitions, and error slices. Prefer the simplest model that clears the product bar.

      Before deployment

      Run load tests, monitor tail latency, validate input schemas, plan fallbacks, and decide who owns incidents and model updates.

      After deployment

      Monitor live performance, drift, fairness slices, cost, business KPIs, and user feedback. Treat insights as inputs to the next iteration.
